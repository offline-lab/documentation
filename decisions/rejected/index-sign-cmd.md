# Rejected: `buildctl index sign` as Standalone Command

**Status:** Not a standalone user command — index signing is an internal step of
`buildctl index update` / `buildctl index generate`
**Replaced by:** Signing integrated into `buildctl index update` and `buildctl index generate`

---

## What was described

Early drafts referenced `buildctl index sign` as if it were a **standalone user-facing
command** to sign an index by itself. The current specs
([build.md](../../docs/specs/build.md), [repository.md](../../docs/specs/repository.md))
still show `buildctl index sign <file> --key <index-key>`, but only ever as an **internal
step inside** `buildctl index update` / `buildctl index generate` — never as an operation
an operator runs on its own.

---

## Why it doesn't exist

The index signing key (the `--index` key generated by `buildctl key generate --index`)
lives on the repo host. Signing the index is not a standalone operation — it is always
performed immediately after the index is updated:

- `buildctl index update` — patches one package entry in an arch index, then signs it
- `buildctl index generate` — regenerates all index files from scratch, then signs each

There is no scenario where you update an index without signing it, or sign an index
without having just updated it. Making signing a separate command would allow an unsigned
index to exist between update and sign — a race condition in multi-publisher repos.

The two-step (flock → update → sign → release flock) is atomic on the repo host.
